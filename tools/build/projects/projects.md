### How to use this list effectively with an AI assistant

1. **Pick one row**, state the goal, constraints, and target platform up front.
2. **Ask for a file-tree / architecture sketch** before any code so you stay scoped.
3. **Build in sprints**: core logic → UI/CLI → edge cases → polish.
4. **Have the AI generate boilerplate, regexes, SQL, and test cases**; you steer the design decisions.
5. **Time-box to ~4 hrs**: if you're still fighting setup at hour 2, simplify (swap a framework for a script, drop a feature).

### Quick tips for squeezing these into one afternoon

- **Start with the data model or core algorithm**, not the UI. Ask the AI to sketch the algorithm in 10 lines first, then wrap it.
- **For the 10 "Learning / Visualizer" projects**, the AI can generate the drawing/animation boilerplate; you supply the algorithm logic and the teaching angle.
- **For CLI / utility scripts**, ask the AI to scaffold argument parsing, help text, and unit-test stubs so you spend the afternoon on the actual transformation.
- **For browser-only projects** (no server), lean on `localStorage`, the Canvas API, and the Web Audio API—zero deploy friction.
- **Time-box ruthlessly**: 15 min setup → 90 min core → 45 min UI → 30 min polish → 30 min test. If a feature isn't in by the UI block, cut it.

### Scoping guardrails for a single afternoon

- **One input, one output.** A worksheet generator that takes a topic and prints a PDF is in-scope; one that also emails parents and syncs to a gradebook is not.
- **Skip auth & hosting.** Use `localStorage`, a local SQLite file, or a single Flask route. Deploy is tomorrow's problem.
- **Let the AI write the boilerplate, you write the rubric.** The pedagogical content (question banks, rubric language, standards lists) is the 20 % that makes it valuable; the other 80 % is CRUD and rendering—delegate that.
- **Test with one real classroom scenario**, not a synthetic dataset. If a Year-3 teacher can use it before lunch, you've succeeded.
